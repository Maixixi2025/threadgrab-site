Apa yang Sebenarnya Dipecahkan Notula

Kebanyakan perkakas Markdown terbagi menjadi dua kubu. Satu sisi adalah editor kode, tempat file adalah kebenaran tetapi sintaks adalah penghalang: seorang manajer produk yang mengedit spesifikasi harus belajar hashtag, asterisk, pipa tabel, dan diff sebelum dapat mengubah satu paragraf. Sisi lain adalah aplikasi teks kaya, tempat mengedit mudah tetapi keluarannya menjauh dari Markdown biasa begitu seseorang menambahkan komentar, tabel, atau embed.

Notula menolak pertukaran itu. Ia WYSIWYG, bukan pratinjau langsung: tidak ada sintaks Markdown yang pernah terlihat di baris kursor Anda, tetapi file di disk tetap berupa Markdown biasa. Anda mengedit diagram Mermaid sebagai gambar dan ia diserialisasi kembali menjadi blok berpagar yang sama. Anda memilih bagian, berkomentar, membalas, dan menyelesaikan, dan git mencatat setiap versi. Tidak seorang pun pernah diperlihatkan rebase, stash, atau kata "detached HEAD".

Di balik layar, ini adalah model docs as code yang memindahkan spesifikasi, PRD, RFC, dan runbook keluar dari wiki dan menaruhnya di samping kode. Perbedaannya adalah antarmuka: Notula memberi orang yang tidak menggunakan git jalan masuk, tanpa menyerahkan file kembali.

Mengapa "Markdown Bersih" Menjadi Syarat bagi Agen AI

Agen membaca, menulis, dan meninjau file .md biasa secara native. File di repositori adalah tempat mereka paling kuat — itu pernyataan yang Anda lihat di beranda Notula dan sejalan dengan cara perkakas agen bekerja dalam praktik. Penyimpanan vektor memotong berdasarkan judul. Perakit prompt merakit seluruh file berdasarkan strukturnya. LLM yang diminta "baca catatan ini" bekerja paling baik ketika catatan itu adalah Markdown tanpa ambiguitas, dengan tingkat judul yang jelas dan tanpa sisa markup.

Apa yang merusaknya?

  • Kekacauan markup. Menempel dari editor kaya menyeret gaya inline, span, dan tag kosong ke dalam file yang seharusnya berupa teks biasa.
  • Judul yang tidak konsisten. Agen yang mengandalkan level ## untuk memotong file panjang akan salah pada dokumen yang mencampur #, ###, dan tebal-sebagai-judul.
  • Konten duplikat atau tanpa tag. Dua versi thread yang sama, satu dengan front-matter dan satu tanpa, memecah cara agen mengambil fakta.
  • Data biner atau shelled. File yang di balik layar bukan Markdown sungguhan — jebakan shell SPA — merusak penguraian sepenuhnya.

Ini persis kelas masalah yang dipecahkan alat konversi pada saat ingest dan alat kurasi setelahnya. ThreadGrab menormalkan sumber: setiap thread menjadi struktur deterministik yang sama — judul, paragraf, daftar, dan blok kode. Notula menormalkan penyerahan: manusia menjaga file tetap bersih dan tersusun sebelum agen membacanya.

Dari Konten Sosial ke Arsip Siap-Agen

Ini alur kerja yang menghubungkan pengarsipan sosial dengan ide Notula. Alur ini mengasumsikan Anda sudah mengonversi post dan thread X menjadi Markdown; jika belum, itulah langkah pertama.

  1. Ingest dengan konverter. Ubah setiap thread publik X menjadi Markdown bersih dengan ThreadGrab. Simpan URL, tanggal terbit, dan penulis di front-matter agar file dapat menjelaskan dirinya sendiri.
  2. Kurasi di editor WYSIWYG. Buka arsip di Notula. Perbaiki judul, gabungkan thread duplikat, tambahkan tag, dan tulis ringkasan singkat di bagian atas setiap file. Edit tetap berupa Markdown biasa di disk.
  3. Commit ke git. Setiap perubahan terversi. Agen AI, indeks vektor, atau Anda di masa depan dapat menelusuri seluruh riwayat dan melihat apa yang ditambah, diubah, atau dihapus.
  4. Beri makan agen. Arahkan agen atau basis pengetahuan Anda ke repositori. Ia membaca Markdown yang rapi dan mengembalikan jawaban yang berdasar, alih-alih menebak dari sumber yang berantakan atau shelled.

Langkah kedua adalah yang paling sering dilewati orang, dan justru langkah yang dibuat mudah oleh Notula. Konversi diperlukan tetapi tidak cukup: folder Markdown bersih hanya siap-agen jika tetap bersih, tersusun, dan tanpa duplikat seiring waktu. Itu pekerjaan manusia dengan alat berbentuk editor, bukan pekerjaan terminal.

Pertahankan Provenansi Saat Mengurasi

Satu catatan sebelum menyerahkan setiap thread terarsip ke editor AI: pertahankan provenansi. Saat Anda mengurasi konten sosial — yang merupakan konten orang lain, betapapun publiknya — simpan source, tanggal arsip, dan penulis asli di file. Jika agen nanti mengutip atau merangkum thread itu, pembaca harus dapat menelusurinya kembali ke post asli.

Uji Pembacaan Agen: Apakah Arsip Anda Benar-Benar Bisa Dipakai?

Sebelum mempercayakan arsip ke agen AI, lakukan pemeriksaan keterbacaan cepat pada beberapa file. Anda tidak butuh LLM untuk sebagian besar; beberapa perintah shell mengungkap apakah Markdown Anda ramah-agen atau penuh jebakan.

# 1. Hitung file yang sebenarnya bukan Markdown
find . -name "*.md" -size +2M -print            # mencurigakan besar = mungkin rich-text atau shelled

# 2. Tandai front-matter yang hilang (provenansi penting untuk arsip sosial)
grep -L "^---" $(find blog -name "*.md") | head

# 3. Temukan level judul yang tidak konsisten dalam satu file
grep -n "^#\{1,4\} " notes/thread-1234.md

# 4. Temukan sisa HTML atau markup yang seharusnya tidak ada di Markdown biasa
grep -rn "

File yang lolos keempat pemeriksaan siap memberi makan agen, penyimpanan vektor, atau basis pengetahuan. File yang gagal pada salah satunya persis seperti hal yang akan diam-diam menurunkan pencarian, chunking, atau pengambilan di kemudian hari. Nilai alat kurasi seperti Notula adalah ia menjaga seluruh folder tetap dalam kondisi lolos, karena edit bersifat visual dan serialisasi deterministik.

Mengapa Markdown bersih penting bagi agen AI?

Agen AI membaca Markdown biasa secara native. Saat catatan, spesifikasi, dan konten yang diarsipkan disimpan sebagai file .md bersih dengan judul yang jelas dan tanpa kekacauan markup, agen dapat menguraikannya dengan andal lalu memasukkannya ke prompt, penyimpanan vektor, atau pipeline. Markdown yang berantakan atau redundan justru menjadi titik di mana penguraian agen mulai gagal, sehingga mengurasi file sama pentingnya dengan mengonversinya.

Bagaimana editor WYSIWYG menjaga Markdown tetap bersih?

Notula bersifat WYSIWYG, bukan pratinjau langsung. Anda tidak pernah menyentuh sintaks Markdown saat mengedit, tetapi file di disk tetap berupa Markdown biasa. Setiap versi tersimpan di git, jadi tidak ada yang berubah di bawah kursor tanpa catatan. Ini adalah pertukaran docs as code: manusia mendapat editor dokumen, agen mendapat file yang terbentuk rapi.
